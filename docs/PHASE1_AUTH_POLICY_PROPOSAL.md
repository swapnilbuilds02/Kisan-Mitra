# Owner-approved authentication policy and implementation status

**Approved 2026-11-27.** Farmer, Shop, Consultant, and Owner/Admin accounts must eventually offer registered mobile plus password, registered mobile plus OTP, password recovery through a purpose-specific OTP, refresh, and logout. The user chooses password or OTP. Mandatory Admin password plus MFA is no longer the default. Stronger optional Admin factors remain a security recommendation because password-only and SMS OTP-only access are exposed to credential theft, SIM swaps, and account recovery abuse.

**Stage 1F source update:** Expo screens now connect Farmer and partner password/OTP, recovery, and registration routes; pending partners use the restricted `/api/v1/auth/session` response. Next.js provides Owner password/OTP and recovery forms through server-only API calls, HttpOnly cookies, CSRF/origin checks, and a protected approval interface. Admin partner decisions now require recent password proof bound to the active Admin session. This is reauthentication for sensitive operations, not mandatory MFA for login. Admin-specific persistent login/OTP limits are prepared in migration `0008`. All frontend and PostgreSQL behavior remains unverified because dependencies and an isolated server are unavailable. No live SMS is active.

Stage 1A introduced the shared password backend and Farmer password login. Stage 1B added Farmer password recovery and authenticated password change. Stage 1C added Farmer password enrollment. Stage 1D added Shop and Consultant application, login, and approval source paths. Stage 1E adds restricted Admin preparation and activation, password/OTP login, recovery, change, and session checks. Mobile UI and web UI remain pending. No live SMS sender is configured.

Stage 1B adds `REGISTRATION`, `LOGIN`, `ACCOUNT_CLAIM`, and `PASSWORD_RESET` challenge purposes to the existing OTP table. The single active challenge per mobile policy means any new challenge replaces and invalidates the older challenge, regardless of purpose. The migration invalidates all pre-existing unlabelled challenges before any new purpose is accepted. The legacy Farmer OTP route issues and consumes only `LOGIN` challenges. A reset OTP is bound to a challenge UUID and Farmer identity, and its keyed code digest cannot be used on the login route.

Stage 1C adds Farmer onboarding behind `REGISTRATION` or `ACCOUNT_CLAIM` OTP. A new Farmer receives a new `users` row only after OTP verification and completion; an Admin-prepared or existing OTP-only Farmer keeps the same `users.id`. The restricted onboarding token expires after 10 minutes and is stored only as a digest. Completion atomically creates the password credential, upserts the existing `farmer_profiles` row, records an approved service-consent document/version, and activates the eligible Farmer. Existing password credentials cannot be overwritten by this path. A session is issued after commit; if session creation fails, the account remains activated and the Farmer can sign in with password or request a new OTP. The current one-challenge-per-mobile policy remains; cooldown and hourly mobile/IP limits constrain replacement attempts.

Stage 1D prepares Shop and Consultant applications. Registration OTPs remain in the existing challenge table but carry an intended partner role; Farmer onboarding rejects a partner-bound challenge. Application completion creates a verified partner identity, one shared `partner_profiles` row, a partner application, password credential, and approved consent record in one SQL transaction. Pending applicants can authenticate into restricted sessions to view their own status/profile and change or recover a password. Approval, rejection, suspension, and reactivation are explicit Admin decisions; approval and suspension revoke existing sessions, so a pending token cannot gain privileged access. Rejected applications have no automatic resubmission path. Editable partner fields are limited to language and location; changes to business identity or qualifications require later Admin review. No relationship or farmer-data access is granted merely by partner approval.

Partner and Admin password/OTP login, password reset/change, refresh, and logout reuse the common auth stack. Admins require a migration-owner prepared identity, an `ACCOUNT_CLAIM` OTP bound to that identity, and one-time password activation before login. The public API has no Admin registration or role assignment endpoint. The migration-owner command itself is privileged: its operator must independently verify any request to prepare an additional Admin, and the claimed `--operator-id` is audit metadata, not cryptographic proof of approval. No actual Owner account is created by source installation. SMS OTP for a privileged role remains vulnerable to SIM swaps and mobile account takeover; optional stronger factors, independent recovery review, and shorter Admin session lifetimes should be considered before live delivery. Shop and Consultant dashboards remain in the mobile app; Owner/Admin stays on the website.

Consent wording remains an Owner decision. Migration `0006` seeds no approved document, so completion fails closed until an operator installs an approved document/version. Isolated database tests may insert an explicitly named `dev-*` version. Existing active OTP-only Farmers retain their OTP access while onboarding is pending; their new password requires the same proof and consent transaction. No Shop/Consultant relationship is created or changed.

Password recovery uses `POST /api/v1/auth/password/forgot`, `/reset/verify`, and `/reset`. A verified reset OTP yields a random 10-minute, single-use authorization; PostgreSQL stores only its SHA-256 digest. Reset completion updates the existing credential, consumes all outstanding reset authorizations for the identity, revokes all sessions, and writes audit events in one transaction. `POST /api/v1/auth/password/change` requires an active session and current password, then updates the credential and revokes sessions in one transaction. Password login now checks the verified credential hash again while creating a session under an identity row lock. These database properties are prepared but not PostgreSQL-verified.

Recovery is available in source for verified, active Farmers, eligible pending or approved Shop/Consultant applicants, and activated Admins with an existing password credential. It never enrolls an OTP-only account, approves a pending partner, reactivates a suspended account, or grants an Admin role. Admin recovery uses the same `PASSWORD_RESET` proof and revokes all sessions after a successful change. Live SMS remains unauthorized.

| Role | Password login source | OTP login source | Remaining gate |
| --- | --- | --- | --- |
| Farmer | Verified, active identity with an internally provisioned password can log in | Existing farmer OTP claim flow | Secure password creation and profile/consent onboarding |
| Shop | Pending restricted or approved session, checked server-side | Pending restricted or approved session | PostgreSQL approval/locking verification and live sender approval |
| Consultant | Pending restricted or approved session, checked server-side | Pending restricted or approved session | PostgreSQL approval/locking verification and live sender approval |
| Owner/Admin | Activated provisioning record, active verified identity, current password | Bound `LOGIN` challenge for the same active Admin identity | PostgreSQL verification, approved OTP sender, sensitive-operation reauthentication, and website UI |

The shared password module uses scrypt from the Python standard library, with random salt and fixed bounded work factors. Password hashes live in `km_private.password_credentials`, linked one-to-one to `users`. Existing OTP-only accounts have no credential row and remain functional. The repository exposes internal create/replace methods; the runtime role is not granted credential mutation. The API returns generic invalid-credential errors and never returns hashes. Password login uses existing RS256 and durable session issuance.

The Stage 1A login limit is stored in PostgreSQL as separate keyed mobile and IP digest counters with a 15-minute window and five attempts for either scope. The database audit event records an attempt without mobile, password, hash, or token. Audit retention and alerting still need operational policy.

The previous farmer onboarding and secure client-session contract remains pending: verify mobile, detect/claim one farmer identity, create password after authorized proof, complete profile and consent, store mobile refresh tokens in OS secure storage, serialize refresh, clear credentials on revocation, and route from server role/state. Owner/Admin web should use HttpOnly Secure cookies, origin validation, and CSRF controls. None of those client flows is implemented in Stage 1A.

Business decisions still pending: farmer assignment confirmation, former-partner historical access, delegated Admin powers, final consent wording, and subscription expiry rules. The login policy itself is approved.
